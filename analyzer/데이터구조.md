# 관계 정보의 생성·저장 구조

## 생성 순서

1. 프로젝트 폴더의 텍스트 파일을 수집한다. 파일별 상대경로와 SHA-256을 기록하고 원본 바이트는 해시 이름의 `blobs/<sha256>`에 둔다. 제외 파일은 스냅샷의 `manifest.omitted`에 사유와 함께 기록한다.
2. Java 파일은 tree-sitter 구문 트리에서 선언·주석·호출 지점을 뽑는다. 같은 경로·내용·파서 버전의 결과는 `parse_cache/`에서 재사용한다.
3. 선언 소유 관계와 상속·구현·호출 **후보**를 연결한다. 호출 대상은 이름·인자 수·문맥에서 추정한 타입으로 좁힌다. 다중 후보나 미해결 호출이 남을 수 있다.
4. 프로젝트 ID, 스냅샷 내용 해시, 파서 버전으로 `snapshot_id`를 만든다. 관련 행을 SQLite 트랜잭션으로 넣고 완료되면 프로젝트의 `active_snapshot`을 바꾼다. 기존 스냅샷은 변경하지 않는다. **같은 파일 바이트여도 프로젝트 ID가 다르면 스냅샷 ID가 달라질 수 있다.**

수집 상한은 텍스트 파일 25,000개, 합계 700 MB, 파일당 5 MB다. Vul4J+의 가장 큰 준비 스냅샷(약 643 MB)을 관계 정보 구성에서 임의로 누락하지 않도록 조정했으며, 새 수집 스냅샷은 `snapshot-v8`로 구분한다. 상한 초과, 링크, 비밀 파일명, 빌드 산출물, 지원하지 않는 형식 및 UTF-8이 아닌 파일은 제외·기록된다. 수집 대상 확장자는 여러 언어를 포함하지만 **구문·관계 해석은 현재 Java 중심**이다. 따라서 “모든 언어의 완전한 호출 그래프”라는 주장은 하지 않는다.

## 저장 위치

지정한 `--data-dir` 아래에 `relations.sqlite3`, `blobs/`, `parse_cache/`가 생긴다. DB는 SQLite WAL 모드를 쓴다. 소스 전문은 `files` 행에 복제하지 않고 SHA-256로 원본 blob을 참조한다. `file_search`는 파일 내용의 문자열 검색용 데이터다. 스냅샷의 `manifest`에는 수집/제외 목록 및 Git 커밋(확인 가능할 때), `metrics`에는 건수·시간·오류·미해결 호출 수, `capabilities`에는 해석 가능 범위가 JSON으로 들어간다.

| 테이블 | 주요 필드 | 의미 |
| --- | --- | --- |
| `projects` | `id`, `root`, `active_snapshot` | 로컬 프로젝트와 현재 활성 버전 |
| `snapshots` | `id`, `project_id`, `manifest`, `metrics`, `capabilities` | 불변 입력 버전 및 생성 메타데이터 |
| `files` | `snapshot_id`, `path`, `hash`, `size`, `language`, `line_count` | 파일 목록과 원본 blob 연결 |
| `file_search` | `path`, `content` | 파일 내용의 문자열 검색용 데이터 |
| `symbols` | `id`, `kind`, `qualified_name`, `owner_id`, `path`, `start_line`, `end_line`, `data` | 선언과 위치·소유자; `data`는 추가 속성 JSON |
| `calls` | `caller_id`, `path`, `start_line`, `data` | 호출 지점 및 후보 대상. `data.status`가 `unresolved`일 수 있음 |
| `edges` | `src_id`, `dst_id`, `kind`, `data` | 포함·상속·구현·호출 등 관계 후보 |
| `facts` | `symbol_id`, `path`, `kind`, `data` | 라우트·입력·권한·설정 등의 단서 |
| `jobs`, `events` | 상태, 단계, 진행률, 기록 | 빌드 작업 추적 |

SQLite의 `files`, `symbols`, `calls`, `edges`, `facts`는 모두 `snapshot_id`로 범위를 제한해야 한다. `symbols.owner_id`는 선언 포함 관계이고, `edges`는 탐색을 돕는 별도 연결이다. `data` JSON의 `status: candidate`는 **가능성 표시**이지 취약점 판정이 아니다.

## 짧은 실제 예

`tests/fixture/Controller.java`의 `item(@PathVariable String id)`가 `service.find(id)`를 호출하고, `Service.java`에 `find(String id)`가 있다. 기능 확인 결과는 파일 2개, 기호 5개, 호출 1개, 관계 후보 4개, 단서 2개였다. `facts`에서 HTTP 경로 `/items/{id}`와 `@PathVariable` 입력 단서를 찾고, 기호 ID로 `relations`를 조회해 연결된 `Service.find` 후보를 따라갈 수 있다. 이는 소스 파일을 차례로 무작정 열 필요를 줄일 수 있는 **탐색 보조 수단**이다. 반대로 실행 시 실제로 그 메서드가 호출되는지, 입력이 위험한 목적지에 도달하는지, 권한 검사가 적용되는지는 소스와 실행 증거를 별도로 확인해야 한다.

같은 시험에서 조회한 핵심 필드는 다음과 같다. ID는 이 특정 파일 내용과 경로에 대한 값이며 다른 프로젝트에서는 바뀐다.

```json
{
  "symbol": {"id": "03671c67b36120394d354495", "qualified_name": "Service.find", "path": "Service.java", "start_line": 2},
  "edge": {"kind": "CALLS", "src_id": "fef88aa808be795c84bc56ab", "dst_id": "03671c67b36120394d354495", "status": "candidate", "evidence": {"path": "Controller.java", "start_line": 9}},
  "facts": [
    {"kind": "route", "paths": ["/items/{id}"], "http_method": "GET", "status": "candidate"},
    {"kind": "input", "parameter": "id", "annotation": "@PathVariable", "status": "candidate"}
  ]
}
```

`CALLS`의 `src_id`를 다시 `symbol`로 조회하면 `Controller.item` 선언과 위치가 나온다. 거기서 원본 몇 줄을 `read`로 확인하는 식으로 관계→소스 확인을 반복한다. 프로그램은 분석 결론 대신 **경로와 근거 위치**를 건넨다.

## 논문에서의 P1 정의

P1은 “원본 소스 + 사전 계산한 관계 후보 데이터에 대한 조회 권한”이다. B0에도 **동일 원본 소스**를 주되 관계 DB/조회 도구는 주지 않는다. 관계 DB가 원본 소스를 대체하거나 정답 패치·취약점 레이블을 제공하는 조건이 아니다. Spring 관련 단서에는 주석·설정 역할 태그가 포함되지만 별도의 규칙 기반 탐지 결과는 포함하지 않는다. 공개 결과와 평가 범위는 [실험 결과 요약](../results/summary.md)에 정리했다.
P1 조회에는 관계 외에 파일 전문 검색과 구문·역할 태그도 있으므로 관찰 효과를 간선만의 기여로 단정하지 않는다.

## 재현·해석 제한

- 구문상의 후보 연결은 동적 디스패치, 의존성 주입, 런타임 프로파일, 데이터 흐름, 제어 흐름, 실제 인가 정책을 완전히 해석하지 않는다.
- 설정 파일 존재는 활성 설정을 뜻하지 않는다.
- 후보 관계만으로 오탐/정탐을 판정할 수 없다. LLM의 최종 후보는 정답 패치·테스트·재현·벤더 판정 등과 따로 대조한다.
- 평가에 사용된 DB는 당시 입력의 해시로 동결했다. 새 버전의 프로그램이 생성한 스냅샷과 행 수가 같다고 곧 같은 입력은 아니다.
