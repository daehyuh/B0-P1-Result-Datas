# VJBench Top-1 형식 오류 보충 재실행 및 판정

작성일: 2026-10-05

실험: DeepSeek-V4.1-Flash, reasoning effort `max`, Top-1, B0/P1

## 핵심 결과

원본 Top-1 실행의 84건은 모두 API 작업 자체는 `complete`였지만, 그중 4건은 사전에 정한 응답 형식을 만족하지 못했다. 이 4건을 원본 기록에서 고치거나 지우지 않고 별도 보충 실험에서 각 1회 다시 요청했다. 새 응답은 4건 모두 형식 검사를 통과하고 후보를 하나씩 제출했다.

주 실행 원장에는 B0 case-003의 첫 시도가 연결 종료로 `ambiguous` 처리된 뒤, 후속 시도가 완료된 기록도 있다. 따라서 리뷰 최종 행은 84건 모두 완료지만, 요청·비용 합계에는 이 시도를 포함한 원장 기록을 그대로 사용했다.

새 후보를 데이터셋이 지정한 취약점과 대조한 결과, 세 건은 지정 취약점과 다른 문제를 제시해 **지정 정답 불일치**로 판정했다. 나머지 한 건은 후보가 정답 취약점과 관련된 코드 흐름을 짚었지만, VJBench에 연결된 수정 커밋이 공식 보안 수정과 일치하지 않아 **판정 보류**했다. 따라서 보충 4건에서 확인된 지정 취약점 적중은 0건이며, 엄격한 분모는 판정 가능한 3건이다(0/3). 판정 보류 1건을 오답으로 세지 않았다.

이 결과는 “후보가 실제 취약점으로 확인된 건수”와 같지 않다. 이번 보충 네 건에서는 새 후보 중 독립적으로 실제 취약점이라고 확정할 수 있는 항목도 확인하지 못했다. 코드를 실행하거나 독립적인 재현 시험을 한 것은 아니다.

## 사례별 정답 대조

### B0 case-021 — Apollo-1 / CVE-2020-15170

모델은 Apollo Portal의 `GET /consumers/by-appId`에서 소비자 토큰이 권한 확인 없이 반환될 수 있다는 후보를 냈다. 데이터셋의 지정 정답은 Apollo **AdminService**에 내장 접근 통제가 없어 설정 API에 접근할 수 있는 문제다. 공식 권고도 AdminService를 인터넷에 노출하지 말라고 안내하며, 수정은 AdminService 접근 통제 추가다. Portal의 소비자 토큰 노출 후보와 구성 요소·권한 경계·근본 원인이 다르므로 지정 정답 기준 **불일치**로 판정했다. 후보 자체를 실제 취약점으로 검증한 것은 아니다.

### B0 case-026 — XWiki-commons-1 / CVE-2022-24898

모델은 `DefaultExtensionSerializer`의 XML 파서에서 외부 엔터티 제한이 보이지 않는다고 보고했다. 지정 정답은 XWiki XML script service를 통한 XML 외부 엔터티 파일 접근이다. 같은 CWE-611 유형을 언급했지만, 모델 후보는 다른 파서·호출 경로를 대상으로 한다. CWE나 제품이 같다는 이유만으로 지정 취약점 적중으로 보지 않고 **불일치**로 판정했다. 별개 경로의 후보가 실제 취약점인지는 별도 검증하지 않았다.

### P1 case-011 — Flow-2 / CVE-2021-31412

모델은 웹 컴포넌트 부트스트랩의 `url` 값이 직렬화되는 과정에서 반사/DOM XSS 가능성을 제기했다. 지정 정답은 Vaadin의 기본 `RouteNotFoundError` 화면에서 요청 경로의 부적절한 처리로 운영 모드의 라우트 목록이 노출되는 문제다. 영향과 핵심 코드 경로가 다르므로 지정 정답 기준 **불일치**다. 제출 후보를 실행해 XSS를 확인한 것은 아니다.

### B0 case-039 — LemMinX-2 / CVE-2022-0671 — 판정 보류

모델은 DTD/XSD 파서 경로에서 외부 엔터티 해석 및 자원 제한이 일관되지 않을 가능성을 제기했다. 공식 GHSA는 CVE-2022-0671을 원격 스키마 다운로드에 따른 blind SSRF 또는 대용량 파일 DoS로 설명하고, 0.19.0을 수정 버전으로 제시한다. 0.19.0 변경 기록의 보안 수정 #1174도 다운로드 프로토콜과 리디렉션을 제한한다. 반면 VJBench CSV의 이 사례 수정 커밋은 #1169 계열의 DTD 검증 동작 문제를 가리키며, CVE 수정 근거와 일치하지 않는다. 모델 후보는 외부 참조·해석 흐름과 겹치는 부분이 있지만, 지정 CVE의 다운로드 목적지·리디렉션 및 대용량 자원 원인을 정확히 특정했다고 단정하기 어렵다.

따라서 이를 적중이나 오답으로 억지 분류하지 않고 **정답 매핑 검토가 필요한 보류**로 남긴다. VJBench 사례의 수정 커밋 연결을 바로잡은 뒤 재판정해야 한다. 이 한 건 때문에 보충 결과의 엄격한 적중률 분모는 4가 아니라 3이다.

## 해석과 제한

- 원본에서 형식이 잘못된 응답은 자동으로 오답 또는 미탐으로 바꾸지 않았다. 보충 호출은 원본과 별도의 새 모델 실행이다.
- 원본 VJBench CSV의 `Used in the study` 열에서 case-021, case-026, case-039는 `No`, case-011은 `Yes`로 표시되어 있다. 따라서 세 건의 판정은 이번 실험 manifest에 포함된 데이터셋 기록에 대한 결과이며, 원 논문에서 사용한 하위집합만의 결과로 일반화하면 안 된다.
- case-026은 로컬 `VJBench_data.json`의 저장소/CVE 표기가 CSV와 충돌한다는 점도 기존 메타데이터 감사에서 확인되어 있다. 이번 대조는 CSV의 저장소와 CVE를 기준으로 했으며, 데이터셋 출처를 인용할 때 이 충돌을 함께 밝혀야 한다.
- 원본의 형식 오류 네 건만 보충했으므로, 이 결과는 84건 전체의 취약점 탐지율을 대신하지 않는다. 나머지 80건의 사례별 판정이 모두 완료된 것은 아니다.
- 형식 유효성, 후보 제출, 데이터셋 지정 취약점 적중, 후보의 실제 취약점 여부는 서로 다른 지표다.
- 보충 후보 중 지정 취약점과 일치한다고 확정한 건은 없다(판정 가능한 3건 중 0건). case-039는 정답 수정 커밋 매핑 문제로 보류했다.
- 모델이 제출한 비지정 후보를 새 취약점으로 세거나, 정적 소스만 읽은 판단을 실행 재현으로 표현하지 않았다.
- B0/P1의 주 실험 원본 DB와 프롬프트, 기존 응답은 변경하지 않았다.
